# 墨边 · 云同步方案

状态：**方案已讨论，尚未开始实现**。写于 2026-11。先用**坚果云（WebDAV）**，后端做成可替换的接口，Google Drive、百度网盘列为以后可选的后端。

目标：同一份书、笔记、待办、目标在多台设备（电脑、将来的 EMUI 手机）之间保持一致；断网照常用，同步在后台进行；宁可停下来也不能覆盖用户的笔记。

## 原则

- **本地优先**：同步是后台的事，不是联网才能用。
- **不依赖 Google / 华为服务**：国内能用，手机和电脑一套代码。
- **先保证不丢数据**：合并有疑问就保留两份，首次同步前先做完整本地备份，可以随时停止同步。
- **每台设备只写自己的文件**：WebDAV 没有锁，这样不会出现两台设备同时改同一个文件。

## 同步到哪里

| 方案 | 结论 |
|---|---|
| **WebDAV（先做）** | 坚果云、群晖 / NAS、Nextcloud 都支持，国内可用，手机和电脑同一套代码。 |
| 同步文件夹（OneDrive、网盘客户端） | 只适合电脑，手机没有；SQLite 放在同步盘里容易冲突。**不采用。** |
| Google Drive | 有官方接口，没有 WebDAV。需要用户自己建 Google Cloud 应用做 OAuth；国内访问需要科学上网。**以后可选，额外约 4~6 天。** |
| 百度网盘 | 没有 WebDAV；开放平台接口要分片上传、取下载链接；非会员的速度和频率限制不明。**以后可选，额外约 6~9 天，需先实测。** |
| 转换工具（AList / OpenList、rclone） | 能把网盘变成 WebDAV，但要有一台一直开着的电脑或 NAS 运行它。 |

后端接口只需要这几个操作：写文件、读文件、列目录、删除、取修改标记（ETag 或修改时间）。以后接别的网盘，只要再写一个实现。

## 同步的是什么

| 数据 | 现状 | 同步方式 |
|---|---|---|
| 笔记、待办、目标、关系线 | 都有 `updated_at` | 按条合并，后改的赢 |
| 书的原文件 | 按内容哈希命名 | 同名即同内容，只增不改 |
| 笔记里的图片 | 同样按哈希命名 | 同上 |
| 书库信息（进度、评分、状态、兴趣） | 存在 `library.json`，**没有修改时间** | 要给每本书加修改时间，或迁进数据库 |
| 笔记回顾的进度 | 没有修改时间 | 要加 |
| 阅读时长 | 按"天 × 书"记录 | **加法合并**：不同设备的时长累加，不覆盖 |
| 回收站 | 有删除时间 | 同样同步 |
| 设置 | 一份 JSON | 只同步通用部分；窗口、缩放、快捷键、卡片位置等**按设备保存，不同步** |
| 书中文字索引 | 可重建 | **不同步**，每台设备自己建 |

## 删除和冲突

- **删除**：现在是直接删，另一台设备不知道，下次同步会把它又传回来。要加**墓碑记录**（只记 id 和删除时间），保留一段时间。回收站 30 天后的彻底删除也要写墓碑。
- **同一条两边都改了**：默认**按修改时间，后改的赢**；输掉的那一版**不丢**，存成"冲突副本"放进回收站，带标记，可找回。
- **待办**：来自笔记的待办以笔记正文为准（现有规则），同步笔记后再对照一遍。
- **标签**：从笔记正文解析，不单独同步。

## 云端的文件布局

```
墨边/
  manifest.json                    这个库的编号、格式版本
  devices/<设备号>.json             每台设备的信息、最后同步时间
  changes/<设备号>/<序号>.json.enc   该设备产生的变更，一次一个文件
  books/<哈希>.<扩展名>              书的原文件
  images/<哈希>.<扩展名>             图片
  snapshot/<日期>.enc               定期生成的完整快照，新设备首次同步用
```

## 同步流程

1. 把自上次以来本地的变更打包，上传到自己的 `changes/` 里。
2. 下载别的设备的新变更，逐条合并进本地数据库。
3. 书和图片：缺什么下什么，有什么传什么，按哈希去重。
4. 更新 `manifest.json` 和自己的设备文件。
5. **首次同步**：先做完整本地备份；云端为空就上传；云端已有内容就先下载合并，合并前给出预览（将新增、更新、删除多少条）。

触发：启动时、之后每隔几分钟、本地有改动后几秒、手动「立即同步」。

## 加密

- 内容在本机用**同步密码**加密后再上传，服务商看到的是密文。
- 密码只存在设备本地；**忘了就无法恢复云端内容**（本地数据不受影响），界面要明确提示。
- 书和图片文件同样加密。
- 默认开启。

## 界面

- 设置里新增「同步」卡片：服务器地址、账号、应用密码、同步密码、「测试连接」、「立即同步」，状态显示上次同步时间、待上传条数、错误。
- 书架和笔记页顶部一个小图标，显示同步中、已同步、出错。
- 冲突副本在回收站里集中查看，带"来自冲突"标记。
- 书的原文件**默认按需下载**（点开才下，或手动"下载到本机"），手机默认不自动下载大文件。

## 需要改动的地方

1. 数据库：给没有修改时间的表补字段（书库信息、回顾进度）；新增墓碑表和变更记录表。
2. 书库从 `library.json` 迁到数据库，或给它按书加修改时间。
3. Rust 新增同步模块：变更导出和导入、合并、加密、WebDAV 客户端。
4. 前端新增同步设置和状态显示。
5. 所有"删除"路径都要写墓碑。

## 坚果云的注意事项（以下来自记忆，S0 要逐项核实）

- WebDAV 地址一般是 `https://dav.jianguoyun.com/dav/`。
- 登录用的不是账号密码，而是在坚果云网页里创建的**应用密码**：账户信息 → 安全选项 → 第三方应用管理 → 添加应用。
- 免费版有**每月上传 / 下载流量**和**请求频率**的限制，具体数字要核实；笔记和待办很小，书的原文件体积大，所以书要按需下载，变更要合并成少量大文件而不是很多小请求。
- 根目录下能否自己建文件夹、文件的修改时间和 ETag 是否可靠，也要实测。

### S0 要探测的事

1. 认证是否通过，能否 `PROPFIND` 列目录。
2. `MKCOL` 建文件夹、`PUT` 上传、`GET` 下载、`DELETE` 删除是否都可用。
3. 返回的 ETag / 修改时间是否可靠，大文件（几十 MB）上传下载的速度。
4. 触发频率限制时返回什么，连续请求多少次会被限流。
5. 单个文件大小上限，路径里中文和特殊字符的处理。

## S0 探测结果（2026-11-14，坚果云免费账号，一次共 72 次请求）

| 项目 | 结果 | 对设计的影响 |
|---|---|---|
| 登录、列目录 | 通过，约 0.6 秒 | 用应用密码即可 |
| 根目录 | 只有一个「我的坚果云/」；在根目录建文件夹返回 **400** | 所有数据放在 `/dav/我的坚果云/墨边/` 下，用户不需要事先建任何东西；逐级用 MKCOL 创建 |
| 在「我的坚果云」里建文件夹、上传、下载、删除 | 全部通过（201 / 200 / 204） | 可用 |
| 修改时间、ETag | `PROPFIND` 能取到，覆盖后 ETag 会变；**`PUT` 的响应里没有 ETag** | 上传后要再取一次 ETag（多一次请求），或用文件名里的序号判断版本 |
| 带错误 `If-Match` 的 `PUT` | 被拒绝（412） | 见下一行：这并不说明 `If-Match` 可用 |
| `If-None-Match: *`（"不存在才创建"） | **没有生效**，覆盖成功（204） | 不能靠它防重名。所有新文件用"设备号 + 序号"的唯一名字，写完再读回校验 |
| 中文名、150 字长名、多级文件夹 | 都通过 | 无限制，文件名仍用 ASCII 的哈希和序号，避免平台差异 |
| 上传 5MB | 1.6 秒（约 3 MB/s） | 够用 |
| 下载 5MB | 第一次 8.7 秒（0.6 MB/s），第二轮 3.3 秒（1.5 MB/s） | 速度**波动很大**；大文件要分段、可续传、显示进度（见下方第二轮） |
| 连续 50 次小上传 | 全部成功，约 6.9 秒，每次 120~180 毫秒，**没有限流** | 每次请求有固定延迟，所以变更要**合并成少量文件**、并行 3~4 个连接；限流的上限还没摸到 |

### 第二轮探测（`DAV_EXTRA`，累计 232 次请求）

| 项目 | 结果 | 对设计的影响 |
|---|---|---|
| `Range` 请求 | 支持，`bytes 0-99` 返回 **206** 和 `Content-Range` | **可以断点续传下载**，可以只取文件的一部分 |
| 重复下载 5MB 三次 | 2.0 / 4.1 / 3.4 MB/s | 第一次的 0.6 MB/s 是偶然；正常约 **1.5~4 MB/s**，一本 50MB 的书约 15~40 秒 |
| 分四段同时下载 | 1.6 秒，约 3.2 MB/s | 并行**没有明显加速**（带宽是瓶颈），分段的价值是**续传和进度**，不是提速；最多用 2 个并行 |
| 上传 5MB | 3.6 秒（1.4 MB/s） | 第一次是 1.6 秒，同样有波动 |
| **带正确 `If-Match` 的 `PUT`** | **返回 412（被拒绝）** | **不能用 `If-Match` 做防覆盖**：正确的和错误的都被拒绝，说明这个服务器不能可靠地处理它（原因未查明，可能是 ETag 的引号格式，也可能是没有真正支持） |
| 连续 150 次 `PROPFIND` | 全部成功，约 18.7 秒（约 0.12 秒一次），没有限流 | 累计 232 次请求没有触发限流；上限仍未摸到，设计上保持请求少而大 |

**结论**：坚果云可以用，但要按它的特点设计：

1. 数据放在 `我的坚果云/墨边/` 下，应用自己逐级创建。
2. **不依赖任何条件写入**（`If-None-Match` 没生效，`If-Match` 不可靠）。所以**云端没有任何"多台设备共同修改"的文件**：每台设备只写自己的文件（`devices/<设备号>.json`、`changes/<设备号>/…`），所有文件名都带设备号和序号，写完再读回校验；`manifest.json` 只在首次初始化时写一次。这和上面的设计本来就一致，现在成了硬性要求。
3. 请求要少而大：变更合并成少量文件，每次请求约 0.15 秒的固定延迟，并行连接数不超过 2~3。
4. 大文件分段、可续传（用 `Range`）、显示进度。速度波动大，要有超时和重试。
5. 免费版每月流量上限仍待你在坚果云账号里确认。

## 流量额度（坚果云免费版：每月上传 1GB、下载 3GB）

额度是设计里的硬约束，决定了"什么同步、什么时候同步"。

**各类数据的大小估算**（要在实现时用真实库核实）

| 数据 | 大小 | 说明 |
|---|---|---|
| 笔记、待办、目标、回顾进度 | 很小 | 2 万条笔记约 20MB 文本，压缩后几 MB；日常变更每天几十 KB |
| 完整快照 | 压缩加密后约几 MB 到十几 MB | 每次生成要上传一次，新设备首次同步要下载一次 |
| 笔记里的图片 | 中等 | 每张几百 KB 到 1~2MB；4000 张约几 GB |
| 书的原文件 | **最大** | 一本 EPUB 约 1~5MB，一本 PDF 几十 MB，扫描版几百 MB；这些文件本身已压缩，压缩没有收益 |

**换算**：每月上传 1GB 约等于 20 本 50MB 的 PDF，或 200 本普通 EPUB。扫描版 PDF 一本就能用掉大半个月的额度。下载额度 3GB，但每台设备读每本书都要下载一次：同一本书在三台设备上看，要下载三次。

**设计决定**

1. **书的原文件默认不自动上传**。同步的是书的信息（标题、进度、评分、兴趣）和你的笔记，书本身由你在书架上**逐本选择"同步到云端"**（也可以批量选），其他设备再点"下载到本机"。这样额度花在你真正想带走的书上。
   - **已确认（2026-11）**：书的原文件默认**一律不自动上传**，特别是由图片组成的扫描版 PDF，体积大、上传没有必要。
   - 选择同步时显示每本书的大小；超过约 50MB 的（通常是扫描版）要二次确认，并显示它会用掉本月额度的百分之几。
   - 书架上用小图标标出每本书的状态：未同步 / 已同步 / 云端有但本机没有。
2. **优先级**：笔记、待办、目标、回顾进度先同步；然后是图片；最后才是书，小文件优先。
3. **额度表**：本地记录这个月已经上传、下载了多少字节，估算剩余额度，设置里显示进度条；达到你设的预算（默认留 10% 余量）就**暂停大文件的传输**，笔记和待办这类小变更仍然继续，并提示"本月额度用完，X 号恢复"。额度的计费周期和计算口径要以坚果云的说明为准，本地数字只是估算。
4. **首次同步前先估算**：库里有多少书、多少图片、总共多大，按每月额度需要几个月，让你选择"只同步笔记和待办"、"同步笔记和图片"或"选择要同步的书"。
5. **压缩**：快照和变更文件先压缩再加密；书和图片不再压缩。
6. **快照不要太频繁**：默认约每周一次，并且只在有足够变更时才生成，避免白白消耗上传额度。
7. **额度紧张的备选**：坚果云付费版额度更大；或者换自己的 NAS / Nextcloud（没有月流量限制）。后端做成可替换接口，正好用得上。

## 风险

- **数据安全**是最大风险：合并有 bug 就可能丢笔记。对策：首次同步前的本地备份、冲突副本不丢、可一键停止同步，并在发布前用大量随机改动的测试验证两边最终一致。
- **WebDAV 各家实现不一样**：要做节流、合并请求、断点续传，并把"服务器行为"集中在一个适配层里。
- **改动面大**：书库迁移和加字段会动到很多地方，分步进行，每一步前都有升级前的数据库备份（已有此机制）。

## 已确认的决定（2026-11）

1. **加密**：默认开启。界面要明确提示"忘了同步密码就找不回云端内容"。
2. **书的原文件**：同步，**按需下载**（点开才下，或手动"下载到本机"）。考虑到免费版每月上传 1GB 的额度，**默认不自动上传书，由用户逐本选择**（见"流量额度"一节）。
3. **设备**：**会有多台手机和多台电脑**，不是只有两台。这一点影响设计，见下。
4. **后端**：先做坚果云（WebDAV），Google Drive、百度网盘作为**以后可选的后端**。

### 多台设备带来的设计要求

- 每台设备在云端有自己的变更目录（已有），新增设备只是多一个目录，不需要改格式。
- **变更文件要能清理**：设备越多、时间越长，`changes/` 里的文件越多。需要定期生成快照，之后把所有设备都已经读过的旧变更删掉；`devices/<设备号>.json` 里记录每台设备已经读到哪里，快照和清理只能在所有活跃设备都读过之后进行。
- **长期不在线的设备**（比如放了半年的旧手机）重新上线时，如果它需要的旧变更已被清理，就从最新快照重新开始，而不是逐条补；本地有未同步的修改时先保留一份冲突副本，再套用快照。
- **设备列表**：设置里显示所有设备（名称、最后同步时间），可以移除不再使用的设备，移除后不再等待它。
- **冲突更常见**：多台设备同时改，"后改的赢"需要可靠的时间依据。设备时钟可能不准，所以每条记录除了时间还带"设备号 + 序号"作为同一时刻的决胜条件；检测到某台设备的时钟与云端相差很大时给出提示。
- **书的原文件**：多台设备可能同时上传同一本书，按哈希命名天然去重，上传前先检查云端有没有。
- **每台设备自己决定是否下载书**：手机默认只同步书的信息，电脑可以选择全部下载。

## 与其他计划的关系

- **EMUI 手机版**（`docs/EMUI-android-plan.md`）：没有云同步，手机版就是个空库。建议云同步的 S1~S2 和手机版的 A~B 并行，或者先做云同步。
- **大规模数据性能优化**（README 路线图）：同步让两台设备的数据量增大，书库入库、列表虚拟滚动、图片缩略图对手机版尤其重要。
